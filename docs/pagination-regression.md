# ページネーションの表示仕様と回帰検証

## 復元する仕様

基準はPR #20直前の `e625932ac90202a02fd3d5c7ff96d40b70532c9e` のWeb表示。
PR #20 (`0f9ef5a`) で候補の総ページ数とページ内の関連件数を混在させた表示を復元する。

- ヒット数は関連判定後の本文の総件数。候補数・文書数・現在ページの件数とは区別する。
- 同じ検索で返された全本文を20件ずつ表示する。
- 総ページ数はその全本文件数を20で割って切り上げる。
- 表示例は `1 / 8ページ（1〜20件 / 151件）`。最後は `8 / 8ページ（141〜151件 / 151件）`。
- 元の表示どおり、1ページ以下ではページ送りを隠す。ヒット数の表示は残す。
- ページ送りは取得済みの同じ結果を使い、検索・判定・要約を再実行しない。
- 新しい検索ではページ位置と前の結果をリセットする。
- 要約のsourcesイベントで全件数と本文を先に表示する。draft/resultを待たせない。
- 要約内の引用リンクから別ページの本文へ移動できる。

検索モデル、関連性の判定方法、候補選択、並列数、APIの判定しきい値はこの修正の対象外。
Webから既存の非ページ分割APIを使う。サーバー側の実装は変更しない。

## 自動検証

`npm test` に含まれるため通常CIで必ず実行される。

| テスト | 検証する動作 |
|---|---|
| `test/pagination-ui.test.mjs` | 実際のindex.htmlとapp.jsを実行し、0・1・11・20・21・40・41・151件の表示、上下のページ操作、欠落・重複、ページ境界、リクエスト回数を確認 |
| 同ファイルの新検索テスト | 次ページに移動してから別の検索を行い、総件数とページ位置をリセット |
| 同ファイルのストリームテスト | 要約完了前の全件表示、生成途中から最終回答までの件数保持、別ページの引用先への移動 |
| `test/pagination.test.ts` のfull-result APIテスト | 候補160件から関連判定後の0・11・20・21・151件を返し、末尾のヒットも保持。search/answer JSONとanswer SSEの件数・本文集合・ID・引用IDを検証 |
| 既存の `test/sync.test.ts` | 全31件を返しながら要約対象を上位20件に限定する既存契約を維持 |

外部モデルは自動テストではモックする。実モデルの検索精度や応答速度を、このテストだけで保証しない。
追加したUIテストを修正前のmainのapp.jsへ適用したところ10件中9件が失敗し、修正版では全10件成功した。APIを20件で打ち切る一時的な変異を加えた場合も、21件を期待するテストが失敗した。変異を戻した後のテストは成功。

## 性能の比較方法

`scripts/benchmark-pagination.mjs` で修正前後の公開資料検索を交互に3回ずつ実行する。
同時実行による競合を避け、順序をラウンドごとに反転する。
検索3質問、要約ストリーミング1質問を測定し、HTTP往復時間・サーバー処理時間・sources到着・最初のdraft到着・完了時間・ヒットIDを記録する。
失敗した要求も記録から除外しない。本文や認証情報は保存しない。

```sh
BASELINE_URL=https://your-baseline.workers.dev \
CANDIDATE_URL=https://your-fixed-version.workers.dev \
node --use-env-proxy scripts/benchmark-pagination.mjs result.json
```

サーバーのデータ・設定は共有されるため、実行中の同期や外部モデルの変動は比較の制約となる。
少数回の中央値だけで全クエリの性能を保証しない。実測で遅延が増えた場合は性能維持を達成したと扱わず、表示修正と無関係な検索ロジック変更を加えない。

修正版はコミット `1f4601917dff2a47c27bac5e1322e31ee3698ac3` の固定プレビュー
<https://53d9f165-trainlcd-decision-rag.catwalk8205.workers.dev/> の全件取得。

### 検索結果の差

ページ単位取得の最初のページと全件取得では、返る本文・出典の集合も異なる。
この比較元の件数は総ヒット数ではないため、件数の増減をそのまま再現率・適合率とは扱わない。
ただし、修正前の初ページにあった出典が全件取得に存在しない例もある。
1回目の地下鉄では MobileApp #236・#237・#447・#448、メトロでは #21・#256・#258・#402・#650・#685、直通では MobileApp #950・StationAPI #342 が該当した。
既存の全件取得とページ単位取得では判定へ渡す件数と文脈が異なる。今回、その検索処理自体は変更していない。
この差のどちらが正しいかの精度評価は未実施であり、「検索結果が同一」とは主張しない。

### 実ブラウザー

固定プレビューで地下鉄を検索し、28件について上下とも `1 / 2ページ（1〜20件 / 28件）`、次ページで `2 / 2ページ（21〜28件 / 28件）` を確認。
20枚・8枚の本文カードと先頭・末尾のボタン状態、前後の移動を確認した。
修正前は同じ質問で `1 / 5ページ（関連本文 15件）`、次ページは `2 / 5ページ（関連本文 6件）` だった。
修正前の初回次ページ取得は自動操作込み2.509秒。復元案の移動4回は0.274 / 0.269 / 1.055 / 1.049秒。
これはブラウザー操作ツールの時間を含む参考値であり、純粋な描画時間や利用者端末の性能ではない。
復元案がページ送りで通信しないことは自動テストで確認した。

### 判定

表示・ページ分割の復元、回帰テスト、型検査、GitHub CIとプレビューの検証は完了。
一方で性能維持条件は未達で、検索結果の差も残るため、PRはDraftのまま。本番への反映は行っていない。
表示以外の変更を行わないという依頼に従い、検索モデル・関連判定・並列数に対する追加変更は行わない。
