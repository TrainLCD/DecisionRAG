# Jevによる意味検索

関連: #51、設計PR #52。2026-11-15。

## 実装

- `backend/src/judge.rs`: TypeSafe公式 `POST https://api.typesafe.ai/v1/systemone`。`TYPESAFE_API_KEY`、版固定の `JEV_MODEL=jev-1.14.0` を使う。質問と候補を同じstateへ入れ、候補ごとのNoul判定をまとめて要求する。
- `backend/src/storage.rs`: 文書候補と本文を共有文脈で意味判定する。本文に明記された直接の根拠と、計算・比較の入力や定義・例外などの部分的根拠を評価する。追加の前提判定は適合率を下げたため採用しない。本文は見出しと段落境界で推論専用の小区間に分け、各区間の具体的な根拠をJevで判定する。コードブロックは途中で分割せず、本文を省略しない。タイトル自体の事実は先頭の保存区間にだけ帰属させ、それ以外の区間では文脈として扱う。保存区間のスコアは小区間の最大値とし、0.5超だけを元の資料IDで一度返す。小区間数による加点や閾値の緩和はしない。まず質問が集合の網羅率・件数を求めるかをJevで一度判定し、追加探索でも同じ判定を再利用する。通常検索は対象・機能・操作・プラットフォーム・明示的な関係を照合する。集計検索は対象集合・データセットの一致を照合し、計算とは別の操作である取り込み条件も保持する。その後、集計検索ではメンバー・単位・包含除外条件・欠落条件を、それ以外では、その質問が求める事実、理由、制約を直接示すかを判定する。手順・設定値への質問に一般的な準備や構成説明を混ぜず、検証結果への質問に単なる試験手順を混ぜない。部分的な回答や明示的なIssue/PRの関係は保持する。対象の一致と根拠の有用性は別の制約であり、スコアを加算しない。
- `backend/src/api.rs`: Jevを既定経路にする。公開範囲を先に確定し、旧ローカル語彙判定をJev結果へ重ねない。本文0件では文書の最低保持枠を30から120へ一度だけ拡大して本文を再判定する。文書の判定結果は再利用し、全候補の再読み込み・再推論を行わない。既存選択文書は拡大時にも保持する。
- 継続ページでは暗号化・認証済みカーソルへ固定した本文位置・スコア・順序を使用する。本文は保存せず、再取得後に改訂・公開範囲・設定モデル版を照合する。既存のカーソル上限200,000文字と15分の期限を維持する。
- `RETRIEVAL_ENGINE=rust-rules-v1` は明示的な切り戻し専用。Jev失敗時には自動切替しない。旧mainは `backup/rust-inference-2026-11-15` に保存済み。

## APIと予算

最大60候補、JSON 24,000 UTF-8 bytes、4並列。バイト上限は保守的な入力制限であり正確なトークン計測ではない。公式APIのコンテキスト制限に達した場合は422として明示し、切り捨てない。文書候補を蓄積する途中にもJSONサイズ合計8MBを検査し、超過時は推論を開始せず422で停止する。1検索につき最大512呼出し、送信JSON合計12,288,000 bytes（512回×24,000 bytes）、判定120秒。再試行と追加探索も含む。

429/529は最大1回再試行し、Retry-After（秒／HTTP日時）を尊重する。待機が30秒を超える場合や期限に収まらない場合は失敗を返す。リダイレクトを追わず、キーや上流本文を利用者のエラーへ含めない。候補IDの欠落・余分なID・重複ID・重複スコアフィールド・型違い・不正な確率を検査する。JSONを通常のMapへ変換する前に重複を検出し、後の値による上書きを許可しない。

`retrieval=jev-semantic-v1`、追加情報は `retrieval_details`。`coverage=bounded` は検索結果の全母集団に対する完全性を保証しないことを示す。Jev APIカーソルのhit_countと総ページ数は確定した関連本文に基づく。Webはこれまでどおり全関連本文を1回取得し、10件ずつページ送りする。APIの `/answer` カーソルは従来どおり現在ページの根拠から回答を生成するため、回答の再利用契約はWebのページ送りに限る。

## 設計全体との境界

このPRはJevによる検索復元の実装。指標レジストリ・全国母集団・本番対応一覧の構造化アダプター・Rustでの割合計算はまだ含まない。検索件数を母数にしないこと、母数・単位・時点が不明な計算は断定しないことを生成指示へ追加したが、プロンプトは数値の正しさを保証するものではない。#51は閉じない。

結果固定には新規D1テーブルを導入せず、既存の認証付きカーソルに小さい位置・スコア配列を格納する。これにより読み取り専用プレビューでスキーマ変更なしに評価できる。上限を超える場合は422で失敗し、将来のサーバー側スナップショットへ移行するまでは黙って縮小しない。

文書の記述は既存のタイトル・抜粋を使用する。見出し索引、低確信度や回答不足をトリガーとした追加探索、バッチ横断の最終再評価は未実装。現状の0.5というNoul判定閾値と30/120という保持枠は初期値で、旧語彙スコアの精度を引き継いだものではない。実モデルでの評価が必要。

## 検証

実Rust/WASM＋SQLiteの `test/jev-retrieval.test.ts` で、元の質問を保持した共有文脈、分散した対応一覧と母集団の保持、42件のページ分割と再推論なし、改訂時409、キー不足・不正応答・上流障害、公開範囲、SSEを検証する。Jev応答はモックであり、意味理解の精度を証明するテストではない。

本番相当のモデル評価は読取専用プレビューで行う。最低でも元の「バス対応の網羅率」、その質問形式、バス対応のキーワード、地名条件、無関係な質問を比較し、資料ID、初回応答、モデル名・トークン・失敗率を記録する。原典との比較や40問の独立ラベル付き評価、本番切替条件は設計PR #52を参照する。未計測を成功とは扱わない。

## 実環境の確認記録

[`evaluation/jev-preview-smoke.json`](evaluation/jev-preview-smoke.json) に読取専用プレビューと現行版の比較を記録した。4問×3回×2経路、すべてHTTP 200。ライブ索引でのスモーク確認であり、固定資料・独立ラベルによる40問評価の代用ではない。

| 質問 | 現行の件数（3回） | Jevの件数（3回） |
| --- | --- | --- |
| バス対応の網羅率 | 0 / 0 / 0 | 39 / 40 / 40 |
| バス対応 | 126 / 126 / 126 | 72 / 69 / 76 |
| どこまでバスに対応していますか？ | 126 / 126 / 126 | 75 / 72 / 69 |
| Apple Watchではバスからの乗換をどう案内しますか？ | 14 / 14 / 14 | 3 / 1 / 2 |

「バス対応の網羅率」は3回ともarchitecture.mdとGTFS導入資料を回収した。これらは対応の説明の根拠であり、全国母集団の完全一覧ではない。Jevの件数は実行ごとに変動した。Apple Watchのケースは旧fixtureのPR #7403をどちらのライブ経路も回収しておらず、件数だけから正しい回答が可能とは判定しない。

Jevの初回検索は約14〜18秒（API計測、生成なし）。1検索あたり約230〜238回のモデル呼出しを要した。ページ継続は合計46件を保持し、cached=true・trace=[]・約1.17秒だった。回答SSEではsources→draft→resultを確認したが、回答内容は対応範囲の説明であり網羅率の算出はしていない。速度・費用・40問の精度条件を通過したとの主張はしない。本番は未変更。

再実行:

```sh
node scripts/benchmark-jev-preview.mjs BASELINE_URL PREVIEW_URL OUTPUT.json
```

このコマンドは24回の検索を行い、Jev側で実モデルの利用費用が発生する。認証済み情報を取得せず、結果には公開資料のIDとスコア、計測値だけを保存する。
