# Jev固定資料評価（Issue #51 / PR #53）

モデル実行前に `test/fixtures/jev-evaluation/{corpus,questions}.json` を固定する。5群×8問、各群の前半4問は開発用、後半4問は評価用。開発用を調整に使い、評価用の結果を見て調整した場合はその集合を未使用評価集合とは呼ばない。原質問は必須回帰として扱う。

資料は既存の公開本文fixture40区間と公開検索のバス関連43区間、明示的に架空と記した地域の台帳・有効化集合・旧時点・未マージ案・非公開資料5区間の計88区間。公開資料は選択バイアスのある抜粋であり、全国母集団でも、本番索引の無作為標本でもない。元の本文区間ID・URL・メタデータを保持し、同一sourceの本文をordinal順に結合した固定索引をSQLiteへ作る。両方式に同じ索引を使う。現行のRust/WASM APIを通し、DBのみローカルfixtureに置換する。旧方式のRustコアはバックアップから変更していない。

正解ラベルは資料に書かれた事実と必要な本文IDの組。`required_groups`の各群は少なくとも1区間を回収すれば成立する必須事実、`relevant_ids`は当該質問の根拠として許容する区間、`fact`はラベルの根拠。ラベルをモデルの取得結果へ合わせて変更しない。誤ラベルが見つかった場合は変更と理由を記録し、旧ラベルの結果も保持する。

## 指標と合否

- 各方式・各質問を3回実行。モデル異常の2問は障害対照であり、通常の関連性精度から除外する。
- 必須事実回収率 = 回収したrequired_groups / 全required_groups。根拠がない問題に再現率を捏造しない。
- 無関係率@10 = 取得上位最大10件のうちrelevant_idsにない割合。結果0件なら0。件数が多いことを精度の高さとみなさない。
- 必須根拠ありなのに0件となる率、必須ケースの全回収、無関係質問の偽陽性を別記する。
- 脱落は本文を読む前の文書選択か、読んだ後の本文判定かを、実際のDB取得IDから分類する。
- 公開資料だけをモデルへ渡すことを検査。非公開fixtureの固有マーカーが入力へ出たら漏出。
- モデル停止と不正応答は502で返り、hit_countを持つ成功応答へ変換されないことを検査する。これら2問は実モデル障害を意図的に起こさず、境界へ障害を注入する。
- 最低ゲート: 必須回帰ケースは3回とも必要根拠回収、漏出0、障害の0件化0。評価用の事実回収率は現行以上、無関係率@10の悪化は5ポイント以内。未達なら不合格と報告する。
- p50/p95、呼出し数、入出力トークンも記録。ローカルSQLite＋遠隔モデルの時間を、本番D1の応答時間と同一視しない。

これは検索精度の評価。架空台帳の正解算術値は分散根拠のラベル付けに使うが、現在のAPIに未実装の集計機能や文章生成の正確性を合格扱いしない。

## 実モデルの実行

`.github/workflows/evaluate-jev.yml` は `evaluation/jev-*` ブランチへのpushで開発用を実行する。`evaluation/jev-heldout-*` なら評価用。APIキーを環境外へ取り出さず、既存WorkerのSecretを継承する評価専用バージョンをアップロードする。本番トラフィックは切り替えない。エントリはモデル呼出しだけでDBを持たず、ランダムな一時トークンで認証し90分後に拒否する。トークンはActionsログでマスクする。モデル入力・出力に秘密値を入れない。

評価本体はNode/SQLiteと実Rust/WASMの同じAPIを使用し、モデル通信だけをこの一時経路へ通す。ラベルはモデル入力へ送らない。結果はActions artifactへ保存し、採用した結果と比較報告を本PRへ収録する。失敗・非200・空の応答も残し、成功した実行だけを選ばない。

## 第1回の結果と第2回の扱い

第1回は開発用20問を実行し、実装・閾値を変えずに評価用20問を実行した。開発用は必須事実回収率75.9%→100%、無関係率25.2%→18.9%だった。一方、評価用は回収率63.6%→95.5%だが無関係率18.8%→30.4%となり、5ポイント以内のゲートを超えて**不合格**。この結果を保持する。

第2回では、本文判定を「話題が関連する」から「質問の指定対象・観点に対して、明記された具体的事実または必要な計算入力を提供する」へ明確化する。数値閾値0.5は変えない。個別の質問・バス固有語・事業者名の例外は追加しない。

第1回の40問は以後すべて開発資料として扱い、ラベル自体は変更しない。`questions-v2.json`の新しい20問を、この修正の実測前に固定した。同じコーパスに対する新しい質問であり、未知の文書群や別ドメインへの汎化を示すものではない。第2回の開発は元40問（split=all）、最終評価はv2の20問。合否条件は変更しない。

固定比較では同期で生成する語彙辞書は空で、Rustコア内蔵の辞書は有効。本番で既に生成された語彙辞書を含む全索引そのものとの精度比較ではない。資料抜粋の選択バイアス、アシスタントが作成した事前ラベル（人手の二重注釈は未実施）、計算・生成回答が評価対象外であることを結果と一緒に明記する。

第1回の完全な取得ID一覧はActions artifactsにも保存:
- 開発: run `43675339963` / artifact `14145657268`
- 評価: run `43675581779` / artifact `14146580771`

リポジトリの第1回JSONはジョブログに記録された全120行ずつの計測値と脱落IDを保存する。取得ID全一覧は上記artifactを参照する。


第2回の厳格化後、元40問では回収率91.5%、無関係率12.3%まで改善したが、原質問の必須根拠が計4回欠けたため不合格を維持した（`jev-development-revised.json`）。欠けた`architecture.md:3`には、認証・取得失敗によって取り込む集合が変わる条件が明記されている。これは測定対象の範囲の根拠であり、ラベルは変更しない。最終修正では、包含・除外・記録欠落の条件も集合の範囲を表す事実と明確化した。質問固有の語や事業者名、閾値への例外は加えていない。

上位10件の適合率も記載する。これは全通常質問の上位最大10件を合算したうち関連ラベルに含まれる割合（micro）で、空結果を含む質問ごとの無関係率の平均とは別指標。事前の合否条件は後者から変更しない。反復実行は同じ質問・資料を使うため独立標本とはみなさず、有意差や母集団精度の推定には使わない。

評価workflowは測定JSONの保存後に固定ゲートを採点し、不合格ならジョブを失敗させる。失敗時もartifactを保持する。過去のworkflow成功は通信・完走を示すだけで、保存された不合格結果を成功へ読み替えない。


第2回最終評価（v2の20問）は回収率56.5%→85.5%、適合率65.7%→78.3%、無関係率19.5%→17.0%だったが、全国の範囲を問う必須B12で一部を説明する根拠を欠いたため**不合格**。この結果も`jev-heldout-v2.json`へ保存する。

第3回では、集合全体の質問に部分集合の事実が寄与することと、それが集合全体の完全性を証明しないことを判定指示で分離する。また、Issueのタイトルに明記された報告・要望も根拠として扱う（要望・closed状態から実装済みとは推定しない）。元40問とv2の20問はすべて開発資料として`questions-development.json`へ結合し、元のラベルは変更しない。次の実測前に`questions-v3.json`の20問を固定した。新しい言い回しだが根底の事実は重複しており、未知文書に対する独立評価とは呼ばない。


第3回の開発60問は回収率96.4%、適合率79.1%まで改善したが、B12で旧調査資料の冒頭追記を2回欠き、不合格となった（`jev-development-v3.json`）。本文には6フィード等の対象が明記されており、元のラベルを維持する。文書の支配的な話題や「調査」という種別で本文全体を落とさず、各事実を判定し、旧資料中の更新追記も日付と限定を保持した根拠として扱う。v3の20問はこの時点でも未実行。


## 注釈の訂正と使用量の扱い

PR #53のレビューで、A1/A2のApple Watch質問にスマートフォン用正方形画面の区間を関連ラベルへ含めた誤りが見つかった。本文を確認して除外した。同じ点検で、網羅率の質問に付けていたGTFSのテスト用抜粋、デプロイ一覧・チェックリスト・変更ファイル一覧だけの区間、符号化された状態データも除外した。これらは実際に対応した範囲の根拠ではない。削除IDと理由は`label-corrections.json`へ記録した。必須事実・質問文・合格閾値は変更していない。訂正は適合率を厳しくする方向に限る。

旧注釈は`questions-original.json`、`questions-development-original.json`、`questions-v2-original.json`、`questions-v3-original.json`に保存した。以後は訂正後の同名質問ファイルを使う。最終開発の取得結果は`jev-development-final-original-labels.json`へ保持し、モデルを再実行せず同じ取得IDを`rescore.mjs`で採点し直したものが`jev-development-final.json`。訂正後も全ゲートに合格した。第1回のローカル記録には取得ID一覧がないため、旧注釈の参考値として残す（完全なIDはActions artifact）。旧・新注釈の値を同じ条件として混ぜない。

使用トークンはモデル境界で実応答から記録する。途中失敗でも既知の量を`observed_*`へ残し、取得できない呼出しがあれば総量は`null`とする。注入した障害対照は実提供元を呼ばないため使用量0。過去の実測では通常検索のエラーは0であり、成功応答のtraceに基づく使用量を保持する。APIの検索応答がエラーなら消費0と仮定しない。


## 直接の根拠と前提根拠の分離

v3の20問は提供元402で一度全通常検索が失敗し、支払い後に同じモデル・質問を再実行した。通信復旧後は回収率30.4%→97.1%、適合率42.1%→73.8%だったが、B14の前提条件を2回欠き、必須ゲートは不合格だった（`jev-heldout-v3-recovered.json`）。通信失敗記録は`jev-heldout-v3-transport-failed.json`に保持する。

これを受け、単一判定で落ちた本文について、定義・包含除外・欠落条件・部分集合の構成員など「必要な前提」をJevで別に判定する。両段階のどちらかが0.5超なら保持し、スコアの最大値で順位付けする。最大値は校正済み確率として扱わない。同点は元の本文順。時間・バイト・呼出予算を共有し、前提判定の障害でも部分成功に変換しない。語句・質問IDの例外は追加しない。

タイトルだけの事実はordinal 0で扱い、後続区間は本文の寄与を要求する。同じタイトルによって符号化状態やチェックリスト区間まで採用する問題を避ける。

これまでの80問を`questions-development-v4.json`へ固定し、別の20問を`questions-v4.json`として次の実測前に固定した。新しい事実を問う質問も追加したが同一コーパスであり、未知文書への汎化を証明する集合ではない。原質問・必須事実・訂正済み関連ラベル・合否閾値は変更しない。


追加レビューでD2（現在も都営だけか）にも網羅率と同じ非根拠区間が残っていたため、同じ基準で関連ラベルから除外した。旧ファイルは`*-before-d2.json`へ保持。テストデータ自体を問うv4のC17はこの除外の対象ではない。訂正対象と理由を`label-corrections.json`へ追記した。

再採点コマンドは`node scripts/evaluation/rescore.mjs INPUT ORIGINAL_QUESTIONS CORRECTED_QUESTIONS NEW_OUTPUT`。元の注釈のSHA-256を記録と照合し、質問文・必須グループの内容・必須指定・モードの同一性を検査する。入力と同じ実体の出力、既存出力への上書きを拒否する。関連ラベルの誤りを取り除く用途に限る。
