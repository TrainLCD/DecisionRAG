# Clef / Clef-flash の検索品質・速度評価案

作成日: 2026-11-12

## 1. 何を判断するか

TrainLCDの開発者がIssue・PR・ドキュメントを横断して、調査や意思決定に必要な情報を短時間で見つけられることを目的とする。

「通常Clefと同じ資料が返ること」は正解の定義にしない。別の資料でも必要な事実が裏付けられれば成功とする。一方、同じIssueが返っても必要な本文が欠けていれば成功にはしない。

まず検索だけを評価し、本文評価や並べ替えをFlashへ変更する価値があるかを判断する。回答の生成・検証は別に評価する。モデルの採否を決める前に、用途と許容できる失敗を明文化する。

## 2. 現状と過去の検証の扱い

現在のコードでは候補選別に主にFlashを使い、長文ドキュメントの個別判定、本文評価、Choiceによる並べ替え、根拠評価・回答検証には通常Clefを使う。`SCREENING_MODEL=clef` は候補選別を通常Clefにする設定であり、全工程をFlashにするスイッチではない。本番の実効設定は比較時に別途記録する。

[PR #19](https://github.com/TrainLCD/DecisionRAG/pull/19)では、全工程をFlashにした試験で修正PRが本文判定から落ち、生成回答が検証で却下されたと報告されている。しかし、事前に定義した正解情報・許容差・十分な質問数がないため、この観測だけで「Flashは不適格」と結論づけない。却下された回答自体が正しかったかも、根拠に照らして確認する必要がある。

[既存の実データ検証](pagination-evaluation.md)と[表示回帰検証](pagination-regression.md)は参考資料とする。過去のページ単位APIと現在の全件取得を混ぜてモデルの性能差にしない。

現行のクラス名 `Jev` はWorkers AIのClefを呼ぶ実装である。「以前のJev」と比較する場合は、当時のコミット・接続先・モデル・入力・設定を特定する。再現できない過去の体感速度を比較値にはしない。

## 3. 最初の評価セット

最初は20問。開発用12問と最終確認用8問を、正解を作った後、モデル比較を始める前に固定する。最終確認用の結果を見て調整したら、その8問は開発用へ移し、新しい最終確認用セットを作る。

下表は質問の候補であり、資料の存在や答えを確認済みという意味ではない。各分類から指定数を選び、重複する話題に偏らないようにする。

| 分類 | 問数 | 質問候補 | 成功に必要な情報 |
|---|---:|---|---|
| 症状から原因・対処を調べる | 4 | 地下鉄で位置更新が止まる問題には何をした？／バックグラウンド測位の復旧方針は？ | 症状と対応の関係。原因未確定ならその区別 |
| 仕様・実装意図を調べる | 4 | バス同士の乗換を表示しないのはなぜ？／経路切替確認が出る条件は？ | 条件と理由。提案と実装済みの区別 |
| 修正・反映状況を調べる | 4 | バス停の重複はどう修正した？／特定の変更はどのGitHubリリースに含まれる？ | 修正内容、マージ状態、確認可能な反映範囲 |
| 表記揺れ・複数資料をまたぐ | 4 | 地下でGPSが戻らない／直通情報の更新が遅い原因と対処／駅番号がない時のウィジェット表示は？ | 語句一致に依存せず必要な事実を結び付ける |
| 根拠不足・似た別問題を区別 | 4 | 資料にない将来対応日は？／マージ済みPRはApp Storeで配信済み？ | 根拠不足を区別し、別件の資料で答えたことにしない |

根拠不足の4問は、固定した評価対象資料で答えを裏付けられないことを確認してから採用する。検索で関連資料が返るだけでは失敗にしない。検索結果の関連性と、回答の断定の可否を混同しない。

運用で重視する5問を「必須ケース」として事前指定する。例は、対処PRへ到達する、仕様変更の理由を拾う、未マージとマージ済みを区別する、過去と現在を区別する、配信を裏付けなく断定しない。必須という重みは利用者の用途に基づく提案であり、AIが特定資料を好むことを理由に付けない。

## 4. 正解の作り方

1. 各質問に必要な事実を1〜3項目へ分解する。例: 「症状」「対応内容」「対応の状態」。
2. リポジトリの原文を直接読み、各事実を裏付ける本文・URL・コミットまたは更新日時を記録する。AIが下書きを作り、開発者が必須事実と用途上の重要度を確認する。
3. 正解は資料IDの単一リストではなく、事実ごとの代替根拠の集合にする。複数資料を合わせて初めて裏付けられる場合も記録する。
4. 同じ出来事でも、症状報告だけでは修正内容の代替にしない。古い仕様や撤回案も現在の仕様の代替にしない。
5. 判定不能な事実は「未確定」とし、採点対象から外す。未確定が残る質問は正式評価セットへ入れない。

通常Clef・Flash双方の結果を集めて見落とした正解資料を追加してよい。ただしモデル名を隠して原文で確認し、同じ改訂版の正解で両方を再採点する。採点者の意見が割れた場合も判定保留とし、都合のよい方だけを採用しない。

評価対象資料に存在しない情報は、検索の取りこぼしとして数えない。同期漏れ・権限の違いは別の問題として記録する。全コーパスの関連資料を列挙したとは限らないため、この方式の値を「完全な再現率」と呼ばない。

### 1問の記録テンプレート

```yaml
id: Q01
query: 地下鉄で位置更新が止まる問題には何をした？
split: development # または holdout
category: symptom_and_fix
critical: true # 提案段階。用途を確認して確定
corpus_snapshot: 未設定
scope: public
answerability: pending # answerable / insufficient / pending
required_facts:
  - id: F1
    description: 原文確認後に記入する対応内容
    acceptable_evidence_sets: [] # 1要素が必要な本文の集合。集合間は代替可能
optional_facts: []
misleading_examples: []
label_status: draft
label_version: 1
```

根拠の各要素には source URL、版、本文位置、確認用抜粋を付ける。非公開フィードバックは公開資料の評価と分け、アクセス権のある保存先にのみ記録する。

## 5. 測る指標

主指標は「1ページ目で用が足りるか」。現在の1ページ10件に合わせる。カードは本文区間単位なので、同じ資料の別区間も実際の表示枠として数える。

| 指標 | 定義・扱い |
|---|---|
| 必要情報充足率@10 | 回答可能な質問のうち、上位10区間で全必須事実を裏付けられた質問の割合 |
| 必要情報充足率@all | 取得した全結果で同じ判定。@10との差は順位の問題、両方の失敗は選別・取得の問題を疑う |
| 必須事実の回収率 | 質問ごとの「拾えた必須事実数 / 定義した必須事実数」を平均。部分的な成功を示す補助指標 |
| 無関係な結果の割合@10 | 先頭最大10区間のうち質問に役立つ事実を含まない区間の割合。0件はN/Aとし、充足率の失敗を隠さない |
| 重複の占有 | 新しい有用情報を増やさない区間が上位10枠をいくつ占めたか。参考値 |
| 検索時間 | クライアント送信から検索結果受信まで。サーバー時間・DB・モデル時間も併記 |
| 安定性 | 各質問3回の充足成功回数、結果集合の変動、エラー率 |
| 使用量 | モデル別呼び出し数、入出力トークン、フォールバック回数。料金は確認できる単価がある時だけ算出 |

回答可能な16問と根拠不足の4問は別集計する。根拠不足の質問には充足率を適用せず、関連する補足と無関係な結果を区別して記録する。

モデルが出す確率は正解率そのものではない。しきい値を変更する場合は開発用セットで調整し、同じ結果への後付け調整と最終評価を分ける。

## 6. 比較する構成と実行条件

まずAとBだけを比較し、Bの結果から次の試験を選ぶ。全組合せを一度に走らせない。

| 構成 | 変更内容 | 目的 |
|---|---|---|
| A: 現行 | 実効設定を記録した現在の混合構成 | 基準 |
| B: 本文Flash | Aの本文評価のみFlashへ変更 | 本文段階の速度と情報回収の差を切り分ける |
| C: 本文・順位Flash | Bに加えてChoiceもFlash | Bが有望なら順位付けも評価 |
| D: 通常Clef | 候補選別も通常Clef、他はA | 問題が候補選別にある場合の対照 |

回答検証はどの検索試験でも通常Clefのまま。本文FlashやChoice Flashは現時点で比較用実装が必要であり、既存の設定だけで切り替えられるとは扱わない。

- 同じコミットを土台にモデル選択だけを変える。しきい値、候補予算、並列数、プロンプト、並び順、ページサイズ、APIモードは固定する。
- 同じデータスナップショットを使う。共有D1なら同期更新の有無を記録し、入力が変わったペアは無効として再測定する。
- Flashの入力上限に収まらない場合、切り捨てない。分割や通常Clefへのフォールバックが必要なら、その差と回数を記録する。「モデルだけの差」と「実際に運用可能な構成全体の差」を区別する。
- 開発用12問を各構成3回、A→BとB→Aを交互に実行する。API計測を同時実行せず、ウォームアップの扱いを事前固定する。
- 有望な構成に絞って最終確認用8問を各3回実行する。モデル名を伏せて採点する。
- 失敗も全要求数に含める。成功要求の時間と失敗率を別々に出し、再試行は元の失敗を消さない。
- 質問ごとの中央値と、同じ質問のA/B比率を示す。全体中央値だけで遅い質問を隠さない。p95は少数標本の参考値と明記する。
- `/answer` はsources到着、最初のdraft、最終resultを別計測する。検索と生成の時間を混ぜない。
- 全件数・総ページ数・ページ送りで再検索や再生成しない契約は、既存の回帰テストで維持する。

保存する記録は実行日時、コミット、実効モデル設定、データ版、質問ID、順序、所要時間、結果IDと順位、事実の採点、エラー、使用量。秘密情報や認証トークンを記録しない。

## 7. 採用の判断案

以下は最初の実測に使う暫定基準。結果を見て変更する場合は理由と改訂日を残し、新しい最終確認用セットで評価する。小規模な試験なので、一般的な品質を保証する数値ではない。

| 判断項目 | 暫定基準 |
|---|---|
| 重要な用途 | 必須ケースについてAが拾えた必須事実をBが失う回をゼロにする。A自体の失敗も別途記録する |
| その他の用途 | 回答可能な各問を3回中2回以上充足で「安定成功」とし、Aから失う安定成功質問は非必須で最大1問。失敗した具体例を採否判断に添える |
| 結果の読みやすさ | 無関係率@10の質問平均がAより10ポイント超悪化しない |
| 体感速度 | 質問別中央値のB/A比率の中央値が0.75以下、かつ質問別短縮秒数の中央値が2秒以上 |
| 信頼性 | 新しく発生したエラーを原因未確認のまま許容しない。特定質問で20%以上遅くなる場合も原因と実害を確認する |
| 最終確認 | 最終確認用セットでも上記を確認。合計値だけで開発用の改善が最終確認用の悪化を相殺しない |

25%かつ2秒という速度目標は、切り替えに見合う体感差を求める初期提案。1問の損失を許すのは「見つからなければ再検索できる非必須用途」に限る。未根拠の断定を許す意味ではない。

数値を満たしても自動で本番変更しない。失った情報と短縮時間を具体例付きで示し、用途上受け入れられるか判断する。必要情報を失わず速くなるなら採用候補、情報を失うなら混合構成の維持や別段階だけの切り替えを検討する。モデルに不確実性を申告させるだけで確実に救済できるとは仮定しない。

## 8. 回答検証は別の試験にする

検索が合格しても、検証モデルまで一緒に変更しない。固定した根拠と回答文を通常Clef・Flashの両方へ渡し、人が原文から付けたラベルと比較する。生成モデルの出力差を混ぜない。

最初は正しい回答10件と、意図的に誤りを含めた回答10件を作る。誤りには、未マージを実装済みとする、マージを配信済みとする、古い仕様を現在とする、条件を捏造する、引用が別件、同時点の矛盾を無視する例を含める。

- 誤った主張の通過率: 低いほどよい。
- 正しく裏付けられた主張の却下率: 低いほどよい。
- 検証所要時間と繰り返しの変動。
- 一部だけ正しい回答、根拠不足、時点の違いを区別できるか。

重大な誤断定の通過が試験で1件でも確認された構成は、原因を解消するまで採用を保留する。ゼロ件でも安全性の保証ではない。PR #19の「回答が却下された」という観測は、この採点で正当な却下か過剰な却下かを判別する。

## 9. 実施順序と成果物

1. AIが20問と根拠の案を原文から作成する。開発者は必須事実・重要な5問・許容差を確認する。
2. データ版とラベルを固定し、開発用12問でA/Bを比較する。
3. 検索の失敗を「候補選別」「本文評価」「順位」「データ不足」に分類し、有望な構成だけを最終確認する。
4. 次の形式で結果をまとめ、採否を決める。
5. 検証モデルの変更が必要なら別試験を行う。本番変更後の不具合は、根拠を確認して評価セットへ追加する。

| 構成 | 必要情報@10 | 必要情報@all | 無関係率@10 | 検索中央値 | エラー/全要求 | 失った情報 | 判断 |
|---|---|---|---|---|---|---|---|
| A | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 | — | 基準 |
| B | 未測定 | 未測定 | 未測定 | 未測定 | 未測定 | 未確認 | 保留 |

本ドキュメントで作成したのは評価設計まで。正解資料の確定、比較用コード、実モデルによる計測、本番モデルの変更は実施していない。
