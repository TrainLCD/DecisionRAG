# 質問に必要な根拠の検索と集計の再設計

作成日: 2026-11-15（JST）。関連: [Issue #51](https://github.com/TrainLCD/DecisionRAG/issues/51)。
状態: 設計。検索エンジン・モデル・本番設定は未変更。実装基点は `95af1304ab8be3040dec6e26db2aba8f65f51ce4`。

## 1. 問題と設計判断

「バス対応の網羅率」のような質問で、計算の根拠になる資料があっても検索結果が0件になる。語彙を個別追加したり、全質問のしきい値を下げたりして対応しない。

検索では元の質問と候補の意味的な関連性を学習済みDecisionモデルで判断する。自由文の検索計画を生成するLLMエージェントは導入しない。文章生成は質問への回答だけとし、チケット要約は復活させない。ただし、検索時の学習済みモデル推論は再導入する。「生成しない」は「モデル推論を行わない」と同義ではない。この点は現行のローカルルール専用方針からの変更である。

Rust/WASMは認証、公開範囲、資料取得、候補構成、探索予算、モデル応答の検査、重複排除、集計、結果の固定、引用対応を担う。実装言語をRustにすることと、意味の判定を文字列ルールに置き換えることを分離する。

集計には別の契約を設ける。関連資料を取得できたことは、全国の母集団や対応数を把握できたことを意味しない。検索結果数・PR数・本文区間数を事業者数や路線数へ読み替えない。

## 2. 論文と現行実装の差

原典: Wan et al., [Retriever-Free Retrieval: Navigating Documents with Decision Models](https://arxiv.org/html/2610.35868v1), 2026。以下の集計・API設計は本プロジェクトの拡張であり、論文の保証ではない。

| 項目 | 原論文 | 現行コード | 新設計 |
| --- | --- | --- | --- |
| 関連性 | §3.2: 質問と複数候補を共有文脈で判定 | `rust/lib.rs::score` は語彙の重み付き一致、複数特徴の一致が2個未満なら最大0.49 | 元の質問から「回答の一部の根拠になるか」を共有文脈で判定 |
| 候補選択 | §3.3: 階層ごとに判定して枝を展開 | `storage::plan` が抜粋を走査、上位30件またはスコア>0.5と参照先を選択 | 意味判定を主経路とし、文字列一致を必要条件にしない |
| 本文 | 候補間の文脈を共有して順位付け | `storage::rank` が独立採点し>0.5のみ残す | 部分的根拠を残し、全回答の充足性とは分離 |
| 取りこぼし | §3.3・§7: 枝刈りは不可逆、予算拡大やdense併用で緩和 | ルール判定後の0件を検索結果として返す | 探索の限界、実行失敗、根拠不足を区別 |
| 集計 | 全母集団の列挙・算術の正確性を保証していない | 回答コンテキストは異なる資料を優先した最大20区間 | 完全性を確認した構造化集合をRustで集計 |

現行式で「バス」と「網羅率」が別特徴になると、バス資料に後者がない場合、本文スコアは最大0.49で除外される。これはコード上の再現条件であり、本番の当該リクエストを採取した実測結果ではない。文書段階の抜粋による脱落も別途測る。

## 3. 検索の処理

1. 既存の認証・公開リポジトリ確認を先に行い、許可された資料だけで検索用スナップショットを確定する。モデルへ渡す候補・辞書・集計データにも同じ範囲を適用する。
2. 質問を改変せず、文書のタイトル・見出し・根拠への参照を持つ記述と一緒にDecisionモデルへ渡す。初期版では文書レベルを直接走査し、リポジトリ単位の粗い枝刈りは行わない。規模が増えたら階層化を評価し、単純走査に対する根拠回収率の損失を計測する。
3. 文書ごとの問いは「この質問の回答、比較、計算に必要な根拠の一部を含む可能性があるか」。質問の全条件や最終的な数値が1文書にそろうことを要求しない。
4. 選んだ文書を本文区間へ展開する。質問・文書の見出し・隣接関係を保ち、複数資料の区間を共有文脈で判定する。問いは「この区間は質問の一部の根拠になるか」。対応一覧、母集団の定義、未対応一覧、条件、時点、相反する記述を、最終回答と語句が違っても対象にする。
5. 関連性と「これだけで回答可能か」を分ける。根拠が足りなくても関連資料は検索結果に残す。Choiceは任意の最終順位付けだけに使い、他の資料を消す根拠にしない。
6. 根拠の不足・低い候補確信度・0件では、一度だけ文書探索枠を広げて再判定する。除外候補を再訪できる候補IDと判定履歴を保持する。これは原論文の不可逆な枝刈りに対する追加策であり、回収の保証ではない。
7. 再探索後も0件なら「探索した範囲で関連資料が見つからない」と返す。タイムアウト、レート制限、予算超過、判定結果の欠損を0件に変換しない。入力資料が不足する場合と計算できない場合も別状態にする。

文字列一致・同期辞書は候補提示、明示的参照の解決、画面の一致箇所表示を補助する。通常の自然言語質問で、未知語や番号があることを理由に全資料へハードフィルターを適用しない。明示的なAPIフィルターはRustで厳密に適用する。質問に番号があるだけでは、指定Issueを引用する修正PRなどを落とさない。

候補記述は単なる本文の間引きでなく、同期時に見出し・節・参照リンク・本文区間の位置を索引化する。生成要約は必須にしない。記述が短い・不明瞭な文書には本文の追加判定枠を確保する。それでも文書選択に限界はあり、`retrieval.coverage` は原則 `bounded` とする。

## 4. Decisionアダプターと探索制御

`backend/src/judge.rs` を追加する想定。入力は `query`、`stage`、許可済み候補IDと説明、モデル・プロンプト版。出力は候補IDごとの関連性スコアとモデル識別子。RustがIDの過不足・重複・範囲外値・NaNを検査し、不正な応答は失敗とする。

共有文脈での並列二値判定に対応したモデルを第一候補にする。固定選択肢による「説明／比較／集計／複合／不明」の意図判定も利用できるが、これは後段の処理を選ぶヒントであり検索を止めるゲートにしない。自由文・SQL・任意コードは生成させない。学習済みモデルの確率も校正済みと仮定しない。

候補分割はトークン予算で管理し、複数バッチのスコアを無条件に同一尺度とみなさない。各バッチの有力候補・境界候補を共通の最終比較へ含める。分割サイズ、候補順序、モデル版を記録して安定性を検証する。採用しきい値・最低保持数・追加探索枠は固定評価セットで決め、現行の0.5を移植しない。

1要求の最大文書数、本文区間数、モデル呼出数、入力トークン、並列数、壁時計時間、推定費用をRustで制限する。再試行・再探索も同じ予算内で行う。超過は明示的なエラーとし、部分結果を完全な結果として公開しない。判定サービス停止時に旧語彙ルールへ黙って切り替えない。

利用する提供元・モデルは未選定。Jev/Clefの過去の速度・料金・容量を現状の保証に使わない。実装前に非生成判定APIの現行仕様、容量、料金、データ取扱いを確認し、同じデータで比較する。条件を満たすモデルが使えなければモデル選定未完了と報告し、生成LLMによる計画生成へ自動変更しない。

## 5. 計算の契約

### 5.1 指標の意味を確定する

網羅率には「全国の事業者」「公開GTFSがある事業者」「路線」「停留所」など異なる分母がある。「対応」もデータ保存・有効化・本番配信で意味が異なる。質問が曖昧なら根拠資料は表示した上で、対象単位・範囲・対応の定義を確認する。黙って全国事業者ベースへ置き換えない。

指標レジストリを設け、`metric_id / unit / scope / as_of / support_definition / source_adapter / completeness_policy` を定義する。モデルは提供された指標・範囲候補のIDを選び、曖昧なら `needs_clarification` を返す。自由文の任意集計を実行する汎用プランナーにはしない。対応する指標がなければ `unsupported_metric` とし、関連情報の回答は続ける。

初期の演算は `count_distinct` と `ratio`。地域・事業者などのパラメーターはアクセス可能な構造化データから列挙したIDを選択する。レジストリの追加はデータ契約の追加であり、質問の言い回しの例外追加ではない。平均・増減などは単位・時点の契約を定義してから拡張する。

### 5.2 母集団と対応集合

文書検索はデータの所在や定義を見つけるために使う。集計そのものは `backend/src/aggregate.rs` とデータごとの読取専用アダプターで行う。

| 集合・属性 | 必要な根拠 |
| --- | --- |
| 母集団 U | 対象単位と範囲が定義された完全一覧、出典、版・時点 |
| 対応集合 S | 同じ単位の有効な対応一覧。データ保有と本番有効化を区別 |
| 同一性 | 安定した事業者／路線ID、別名や統廃合の対応。名前一致だけで自動統合しない |
| 完全性 | 提供元の一覧の定義と全件取得完了。未取得ページ、欠損、エラー、解釈不能行を記録 |
| 時点 | 両集合で比較可能な有効日またはスナップショット。異なる時点は自動合算しない |

Rustは `N = |U|`、`M = |U ∩ S|`、`rate = M / N × 100` を計算する。`N=0` は定義不能。整数の分子・分母と丸め方を保存し、集合の重複、UにないS、曖昧なID、古いデータを検出する。Uが不完全なら割合を出さない。Sが不完全なら完全な対応率として出さない。確認できた件数を述べる場合は範囲を明記し、全体数と区別する。

全行を読み切ったことだけでは、現実の全国一覧の完全性は証明できない。`completeness_policy` は提供元の定義・範囲の根拠も要求する。モデルによる関連判定を全件実行した結果を、完全な母集団と呼ばない。

現在のD1はIssue・PR・文書と本文区間を保持する。全国の母集団、安定した事業者ID、本番対応一覧、完了済み集計スナップショットを保証するスキーマはない。したがって初回から全国対応率を出せるとは約束しない。StationAPI側の実際のデータ定義を調査し、利用可能な一覧と本番有効化の出典を確定してからアダプターを実装する。不足なら `missing_population` 等を返す。他リポジトリや外部データの収集範囲を勝手に広げない。

集計スナップショットの保存が必要になったら新規マイグレーションでマニフェストとメンバーを追加する。`metric_id / scope / as_of / source_revision / adapter_version / expected_count / loaded_count / error_count / completeness_state` と根拠参照を保存し、全バッチ完了後にだけ公開する。途中の更新や複数版を混ぜない。アクセス範囲は元資料から継承し、非公開集合の件数も公開しない。

### 5.3 回答へ渡す結果

集計結果は `status / metric_id / definition / numerator / denominator / value / unit / as_of / source_refs / missing_requirements` を持つ。未成立の数値は `null`。状態は `computed / needs_clarification / missing_population / missing_supported_set / incompatible_scope / empty_population / unsupported_metric` を区別する。

母集団の全件取得が確認できても対象数が0なら `empty_population` とし、割合は `null` にする。母集団を取得できない `missing_population` と区別する。

計算値・定義・対象・時点・出典はRustの確定した表示として返し、LLMには説明文だけを生成させる。LLMが別の割合を生成しても集計値として採用しない。通常の引用検査に加え、集計IDと根拠集合の版を対応付ける。回答の最大20区間から数を数えさせない。説明文内の数値も同じ集計IDの確定値・単位と照合し、照合不能または不一致なら説明文を表示せずRustの確定値だけを表示する。これは引用検査とは別の必須検査とする。

## 6. API・画面・エラー

`/search` と `/answer` に同じ意味検索を使う。`/search` は回答生成を行わない。`/answer` だけが必要に応じて指標選択・集計・説明を行う。元の質問は回答まで保持する。

既存の `evidence / hit_count / pagination` は資料検索の結果として維持し、母集団の数に流用しない。追加フィールドを `retrieval: {engine, coverage, snapshot_id, examined, selected, expanded}` と `aggregation` に分離する。ただし現行 `retrieval` は文字列なので、互換版では文字列を維持して追加オブジェクトを `retrieval_details` とする。全面置換はAPI版変更時だけ行う。

検索結果は一度確定した集合からWebの10件表示と総ページ数を作る。モデルの再実行をページ送りへ持ち込まない。現行APIカーソルは候補本文を20区間ずつ採点する方式でWebとは異なるため、移行版では検索結果スナップショットを保存してそのID・offsetをカーソルへ入れる。旧カーソルを新エンジンで解釈せず409で再検索を求める。元資料の改訂・削除・公開範囲変更・モデル版も検査し、閲覧権限喪失時は保存済み本文を返さない。

結果保存先はD1の専用テーブルを想定し、期限付き・scope拘束・サーバー側に限定する。追加スキーマ、サイズ上限、削除ジョブ、索引更新時の無効化を結果固定の実装PRに含める。Service Workerや共有CDNへ結果を保存しない。

SSEは `sources → draft → result` を維持する。検索確定後にsourcesを先に送り、集計や説明生成の完了を待たせない。新しい集計状態は既存イベントの追加フィールドで渡す。SSE開始後の判定・集計サービス失敗はerrorイベントで通知し、sourcesは保持する。算出不能はサービスエラーと区別し、根拠と不足条件をresultで返す。再検索ボタンで回復できることを検証する。

引用の意味的な正しさ・現在仕様の確定は別の問題であり、Decisionモデル導入だけで検証済みにしない。既存の時点・PR/Issue種別・公開範囲・引用整合性の検査を維持する。

## 7. 評価とリリース条件

修正前の結果を正解としない。同じ資料スナップショットに、原文の根拠IDと必須事実を独立に付ける。モデルや辞書調整に使う開発集合と、最後まで調整に使わない評価集合を分ける。旧モデルの評価計画の考え方は継承するが、過去の混合Clef構成を現行基準にしない。

初期セットは少なくとも40問、各群8問を用意する。各群を開発4問・評価4問に分割し、各質問を3回実行する。これは着手時の評価設計であり、未測定の精度保証ではない。

| 群 | 例・失敗条件 |
| --- | --- |
| 質問とキーワードの対 | バス対応／どこまでバスに対応しているか。言い換えで必要資料が消えない |
| 集計・分散根拠 | 網羅率、未対応件数、分母と分子が別資料。単一資料に最終回答がなくても回収 |
| 条件・識別子 | 群馬限定、未知の事業者名、Issue番号、否定。条件を落として無関係な回答にしない |
| 時点・矛盾 | 旧「都営のみ」と追加対応、未マージPR、データ保有と本番有効化の違い |
| 不足・障害・境界 | 母集団なし、指標曖昧、非公開資料だけに根拠、判定API障害、真に無関係な質問 |

検索評価は必須事実の回収率、根拠IDのRecall@all、無関係率@10、回答可能なのに0件となる率を報告する。段階ごとの脱落を文書選別／本文／順位／データ不足に分解する。集計は単位、重複排除、集合の版、分子・分母・丸め結果を既知の集合と完全一致で検証する。

元の「バス対応の網羅率」を必須回帰ケースに含める。必要根拠は、対応一覧・その対応の定義と時点、母集団の一覧または母集団未確定と判断できる根拠である。既知の評価集合にあるこれらの根拠を3回とも回収することを必須とし、母集団欠損を検索0件へ変換しない。

最低リリース条件: 必須回帰ケースは3回とも必要根拠を回収し、不正な母数・非公開情報の漏出・実行失敗の0件化は0件。評価集合の事実回収率が現行以上かつ無関係率@10の悪化が5ポイント以内であることを暫定ゲートとする。満たさない場合は例外語を追加せず、失敗段階を見直し、新しい未使用評価集合で再評価する。0件でも一般的な完全性の保証とはしない。

速度・費用はローカルCPU、D1待ち、モデル、検索初回sources、回答初回draft、最終resultのp50/p95、トークン、呼出数、費用、429/503率を記録する。論文の0.7–1.8秒を本サービスのSLOにしない。許容遅延・費用の数値は提供元実測後、本番切替前に設定する。未設定なら切替不可。Workersの同期処理中の時計制約を踏まえ、表示上の0msをCPU時間ゼロとしない。

実Rust/WASMのAPIテストに加え、実モデルでの評価と本番相当の読取専用プレビューを行う。ブラウザーでsourcesの先行表示、ストリーミング、次・前ページ、再生成なし、集計不能の説明、エラー後の再検索を確認する。

## 8. 実装単位と移行順序

| 順序 | 変更 | 完了条件 |
| --- | --- | --- |
| 1 | 固定資料・40問・根拠ラベル・現行計測、モデルAPI調査 | 失敗段階と比較条件を再現可能にする |
| 2 | RustのJudgeアダプター、モデル契約テスト、予算管理 | 非生成の共有文脈判定、欠損や障害を明示。模型テストだけで精度合格にしない |
| 3 | 文書→本文の意味検索、追加探索、結果スナップショット、互換API | 質問の言い換え・分散根拠を回収、ページ送りで再推論しない |
| 4 | 指標選択、レジストリ、対象データ調査、集計アダプター | 完全な集合では正確に算出、不完全・曖昧なら不足条件を提示 |
| 5 | sources先行の回答経路と集計表示、評価・移行 | 精度、費用、実ブラウザー、権限境界の条件を通過 |

各実装PRは#51を参照する。設計PRではIssueを閉じない。検索修復と集計基盤を別PRにできるが、後者の未完了を隠して「網羅率に対応済み」としない。
